# design-course — design a course from its outcomes

This skill is an ordered checklist: each step opens when the one before it has produced its result. The order is the point. A course designed forwards — topics first, then activities, then whatever the topics happen to allow the exam to ask — produces outcomes written afterwards to describe what was already built. They describe it accurately while claiming levels nothing reaches. Designing backwards from the outcomes is what makes the claim true.

What an outcome has to be, and the two directions alignment is checked in, are in the `learning-outcomes` skill — read it before step 4. This skill writes the design; `make-exam` builds assessments on it and re-checks the outcomes before it does.

**Where the artifacts go** is the host project's decision. Absent a rule, the default is a `design/` folder beside the subject's other material, holding `outcomes.md`, `assessment-plan.md`, and `teaching-plan.md`. That is a skill default rather than a shared layout, because no other skill in this set writes these files yet.

## Steps

1. **Discover the project's conventions** — read the host project's agent instructions file (`AGENTS.md`, or `CLAUDE.md`) and inspect an existing course design: folder layout, file naming, available templates, the language the project writes in, and whether the project or the institution fixes the form a course design takes. A project's own rules override the defaults here; an institution's mandated form overrides the document shapes below, and the design is recorded in whatever fields that form provides.
2. **Find what the course owes upward** — the programme outcomes, the curriculum map naming which of them this course is responsible for, and **which revision of the programme is in force for the cohort being taught**. Where a course is taught to two cohorts under two revisions, it owes both, separately. Name every one of these that is missing rather than inferring it: outcomes written without the map are the course's own invention, and they will not survive the first programme review.
3. **Read the course as it is defined** — the official course description, its credits, its contact hours per session, the number of sessions, and any assessment the institution fixes centrally. These are the constraints the design has to fit; take them from the documents rather than estimating.
4. **Write the outcomes, and check them before anything rests on them** — draft them, or collect the ones that already exist, then run every check in the `learning-outcomes` skill: the four ways a verb fails, the count, and the mapping in both directions. **Put every failure to the user and stop** — a compound outcome cannot be repaired downstream, only split, and splitting it after the marks are allocated means reallocating them. An outcome inherited from an approved syllabus that fails a check is reported with what it would have to become, since changing it may need approval this skill cannot give.
5. **Decide how each outcome is evidenced, before the schedule exists** — for each outcome, the assessment that elicits its own verb, in a format whose level it can reach, and its share of the marks. Deciding this after the timetable is what produces a course assessed by whatever fits in the weeks that were left over.
6. **Build the teaching plan** — session by session: the topic, the outcome it serves, and the activity through which learners actually perform that outcome's verb. Every outcome gets sessions; every session names its outcome, or is marked explicitly as serving none. A session serving no outcome is not automatically wrong — an orientation or a review is legitimate — but it is stated rather than left to be noticed later.
7. **Reconcile the alignment table** — one row per outcome: outcome, teaching hours, activity, assessment, marks, programme outcome. Then apply the three rules in the `learning-outcomes` skill: the verb is the same all along each row, every block of marks has an outcome that owns it, and no high-level outcome carries trivial weight. This table is what the assessment work reads afterwards, and what an institution's own form is filled from.
8. **Write the artifacts** — the outcomes, the assessment plan, and the teaching plan, in the project's templates where it has them and in the project's language. Record which programme revision the outcomes map to, and the date the mapping was checked, since a curriculum map goes out of date without the course changing at all.
9. **Verify before finishing** — run the project's check script where one exists, then confirm: every outcome passed the step 4 checks or was raised with the user; every outcome maps to a programme outcome and every programme outcome the course is assigned is reached; every outcome has teaching hours, an assessment whose format reaches its level, and a share of the marks; every session names its outcome or is marked as serving none; the marks sum to the course total; and no row of the alignment table changes its verb along the way.
