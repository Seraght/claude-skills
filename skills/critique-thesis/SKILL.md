# critique-thesis — critique a student thesis

This skill is an ordered checklist: each step opens when the one before it has produced its result. Its findings rest on numbers recomputed from the book and sources looked up outside it, never on an impression of the text. The checks and the report's shape are in [THESIS-CHECKS.md](./THESIS-CHECKS.md) — read it before step 4. It writes the critique and nothing else: the thesis is never filed into the vault, because it carries students' names and IDs.

Whenever a step puts more than one decision to the user, it asks them in the round shape the `grill-point` skill gives in its step 3.

The critique's text lives in a Markdown file beside the Word file, and the Word file is rendered from it: a later change is made in the Markdown and rendered again, rather than in a script that carries the critique's text and is lost with the session.

## Steps

1. **Discover the project's conventions** — read the host project's agent instructions file (`AGENTS.md`, or `CLAUDE.md`) and inspect what it names for thesis critiques: where a critique is written (often outside the vault, since it is about named students), how the file is named, the renderer that turns the Markdown into the institution's Word layout and an example critique in that layout, the thesis regulations or interpretation criteria the institution sets, and the language critiques are written in. Where the project names none of these, ask; a critique saved into the vault beside its notes is personal data in the vault. Then show the user the plan for this run — its steps by number with a 🛑 on each one that stops for the user, then one line of what this step found and one of what it could not find, labelled in the user's language — and wait for the user's go-ahead, or take the dispatch as the go-ahead when this run was sent to work without the user, as a sub-agent; name each later step by its number as it starts.
2. **Locate the thesis and decide which run this is** — the thesis file, usually in staging; whether the user sits on its committee or advises it; and whether an earlier critique of the same thesis exists. Look for one by title and topic in the critiques folder, not only by what the user calls it: a resubmission can arrive described as another group. Where one exists this is a **revision run**: find the earlier critique as it was sent (a copy the students returned may be a re-save; compare the two), and the version it critiqued if the user has it.
3. **Extract the text, page by page** — read the thesis as text, with a marker for each page so every finding can cite one. A Thai extraction that comes out as digits and Latin letters only is the extractor's encoding, not a missing text layer: use one that writes UTF-8 before concluding the text is absent, and copy a file with a Thai name to an ASCII one where the tool cannot open it. A page with no text layer — a scanned certificate, a signed approval — is listed for the user to look at, not read as an image, since an image read misreads names and numbers. The extracted text stays in the session's scratch space and is deleted with it.
4. **Run every check** — work through every group of [THESIS-CHECKS.md](./THESIS-CHECKS.md) against the whole book and write the evidence table as you go: one row per check per place it applies, including the checks that found nothing and the ones that cannot apply here, each with why. Recompute rather than estimate; look sources up rather than recall them. On a revision run, build the status table of the earlier findings first, then run every check on the whole revised book, since a revision breaks things outside what it changed.
5. **Triage the findings** — sort them into the report's sections by severity, merge findings one change resolves, and drop any finding that cannot cite a page and quote or recompute its evidence. Name people by role, never by name or ID.
6. **🛑 Summarise in the chat and wait** — the overall verdict, the critical findings each in a line with its page, the counts per section, and the checks that could not run with what stopped them. The user reads this before any file is written: they sit on the committee and decide what goes to the students, and a finding they reject here costs a line rather than a rebuild. Apply their changes to the findings before going on.
7. **Write the critique** — in Markdown, in the order [THESIS-CHECKS.md](./THESIS-CHECKS.md) gives under *Reporting* and in the layout of the project's example critique, saved where step 1 found and named as the project names critiques; a revision run's name says it is the revised version's critique. Save the evidence table beside it.
8. **Render the Word file** — with the project's renderer, from the Markdown. Where the project has none, build the file under the `thai-office-files` skill's rules. Either way the file is finished only when the rendered check in the `thai-office-files` skill has passed.
9. **Verify** — Run the project's check script where one exists, then confirm: every finding in the critique cites a page and carries its evidence; the evidence table holds a row for every check in every group, including the empty ones; on a revision run, every earlier finding has a status; the critique and the Word file name no student, advisor, or committee member, and carry no ID or phone number; the Word file was rendered from the Markdown beside it; the rendered check's evidence table exists; and nothing from the thesis was written into the vault.
