# A contributed pool is adopted, then critiqued in a new session

A course's 2569 final was written by the instructor who taught it, not by the vault's owner: fifty multiple-choice items, no slides, to be cut to forty-five and brought to the vault's standard. Two sessions worked on it.

The first was asked to "assess it against our criteria in order to import it". No skill fired: the request did not read as `critique-mcq`'s "hands over a paper to check", and "import" is the word `digest` answers to. The run improvised an exam set — research, blueprint, items, paper — and decided for itself which outcome each item served, the inference `critique-mcq` step 2 tells a critique to report as missing rather than make. It stopped at 628K tokens of context when the user said it was full, and wrote its handoff into the session's scratch folder, where no later session would look.

The second ran six jobs in one context: harmonising the wording with another course's paper (150K tokens before any skill was named), `critique-mcq`, writing replacement items for the levels the pool lacked, a Word file for the external reviewer, the user's own review of that file, and a second Word file. It reached 714K tokens and stopped on the plan's usage limit, not the context window. 353 requests averaged about 408K tokens each: 144M tokens read from cache, 5.8M written to it, 0.9M of output. Two cache rewrites of 352K and 627K followed the host dropping old thinking blocks, and typing `resume` after the limit reset rewrote 632K more. The run wrote 28 scripts into its scratch folder, about 250K characters of tool input, many of them carrying the items' Thai text, and the previous session had written its own `measure.py` and document builder the same way.

Three things went wrong, and none of them is a long skill. The work had no skill to enter by. A critique that [ADR 0020](0020-a-run-that-outlasts-a-session-leaves-a-handoff.md) expected to run in a fresh context ran as the second job of a long one, with no handoff to end it at. And the cost of every revision was set by the size of the context it ran in, which was set by everything done before it.

We decided eight things.

**A contributed pool has its own checklist, `adopt-pool`.** [ADR 0006](0006-how-a-skill-is-reached-and-when-it-is-split.md) splits skills by how they are reached, and this is reached differently from both neighbours: `make-exam` starts with no items, `critique-mcq` starts with an assembled paper, and this starts with someone else's items and ends with an exam set ready for review. It keeps the pool word for word in `08-contributed.md`, fixes the blueprint, places and selects the pool against it, writes items for the empty cells, brings the wording to the house style, and assembles the paper, key, and — for constructed-response items — rubric. It ends by recording the review as an unticked item and handing the user the line that starts `critique-mcq` in a new session, rather than in a sub-agent as `make-exam` sends it: a critique's approval and applying would come back into this run's context, which is the context this decision exists to end. Its scope is written papers; a practical stays with `make-practical` ([ADR 0011](0011-a-practical-is-a-different-chain.md)). `critique-mcq` reviews selected-response items only, so any other format is recorded as not yet reviewed.

**The blueprint comes from the outcomes, even when the items came first.** A table read off the pool certifies the pool's proportions instead of checking them: built that way, the paper that had no item at the application level would have had a blueprint with no such cell. So the blueprint is settled at a grill point from the outcomes' weights and the teaching plan before any contributed item is placed, and the cells left empty or short are the gaps. The same grill measures the style budget from the paper the user names, so the rewording has a number to count against. Placing the pool then tags each item with the outcome it serves — the inference a critique reports rather than makes — so it is made in the open and put to the user, and the review later checks each item against tags the user approved. CONTEXT.md now says a blueprint precedes the first item *selected or written*.

**Harmonising changes wording, not what is tested.** The vault's owner did not teach the course, and keeps the contributor's content so that nothing on the paper is something the class was never taught. An item whose repair would change what it tests is cut through the user and its gap filled, not rewritten in place. The house style comes from the vault's decision records and an exemplar paper the user names; a style rule found during the run that should hold for every paper is settled at a grill point and recorded.

**`critique-mcq` joins the checklists that write a handoff.** ADR 0020 left it out because it "already runs as a pass in a fresh context by design", and said it would join once a run was seen to outlast a session. Strictly, none was: here the critique was one job inside a long session, never a run of its own. It joins on the mechanism instead. A critique now takes a reviewer's findings as well as its own passes, so its approval at step 11 opens rounds — apply, rebuild the file, read the reviewer's comments, apply again — that in this case ran from the critique's start to the usage limit and past a `resume`. Step 11's stop is where such a session can end.

**A handoff is named for the skill that wrote it.** Two resumable skills can now stop in one exam set: `make-exam` sends its review to a sub-agent while its own handoff still stands, and an `adopt-pool` handoff survives if the session ends before the run's last step. A single `HANDOFF.md` would be read by whichever skill came next as its own, and deleted by the wrong run. `HANDOFF-<skill>.md` gives each run its own file. The resume clause reads only its own skill's, leaves another's as it is, and reads a finished run's files as material to build on rather than as a run to resume — so the independent pass and a round of reviewer findings start fresh instead of concluding there is nothing left to do. This amends ADR 0020's file name; the three clauses stay held identical by `check.py`.

**A reviewer's findings join a full critique pass.** The user's own review of the Word file, and the external reviewer's, are findings like the passes' own: each is located with the user to the span it is about before triage, goes into the same approval table, and every item it changes is re-measured. Steps 1–8 run as for any paper, because every applied rewrite voids the table the previous pass built. A finding that asks for a rule over every item — order the options by length — is a decision for the vault, settled at a grill point before it is applied. The report takes the next free `1x` number, leaving the earlier one as it stands.

**Scripts outlive the session that wrote them.** In `make-exam`, `critique-mcq`, and `adopt-pool`, a measuring or building script is run from where the vault keeps its scripts, or saved there when written, and an item's text is changed in the items file rather than in a script that regenerates it. `check.py` holds the clause identical and requires it of those three by name. The scripts themselves belong to the vault, since a document builder is one institution's form ([ADR 0013](0013-true-everywhere-or-true-here.md)).

**The rendered check runs in a sub-agent where the host has them.** The sub-agent loads `thai-office-files`, writes the page images and the evidence table beside the file, and reports the breaks inside a word; the building run opens the evidence table before accepting the report, so a report of no breaks cannot stand in for a check that did not run ([ADR 0008](0008-a-check-that-leaves-no-evidence-did-not-run.md)). Thirteen page images then never ride in the building run's context.

## Considered Options

- **Extend `critique-mcq` to build the exam set when none exists** — rejected: a critique changes nothing until the author approves, and building a blueprint and an items file before approval breaks that.
- **A mode of `make-exam` for items that already exist** — rejected: it would skip the sketches and the writing steps that are most of the chain, and two invocations in one file is what ADR 0006 splits.
- **Widen `critique-mcq`'s description only** — rejected: the harmonising and the blueprint would still have no home, and the first session's job was not a critique.
- **Read the blueprint off the pool and call it a coverage map** — rejected: it cannot show a gap, and every skill downstream reads a blueprint.
- **Call the pool a source paper** — rejected: a paper is a sitting that happened, and this one has not; CONTEXT.md defines **Contributed pool**.
- **A separate skill for reviewer feedback** — rejected: its output is the same findings, approval, and re-measurement as `critique-mcq`.
- **Reuse the last pass's measurement table when reviewer findings arrive and nothing has changed** — rejected on review: a table of lengths and spans cannot show that no item changed, and every applied rewrite changes one, so the branch would almost never fire correctly.
- **Keep one `HANDOFF.md` and record the skill inside it** — rejected: two runs in one folder would still overwrite each other's file.
- **Send the review from `adopt-pool` to a sub-agent, as `make-exam` does** — rejected: the approval and applying return to the adopting run's context.
- **Ship the scripts in the skills** — rejected: what is generic in them is short, and what is long is one institution's document form.
- **Warn on context size from inside the skills** — rejected for the reason in [ADR 0018](0018-a-threshold-the-skill-does-not-give-is-one-the-agent-invents.md). The host-side signals — a hook that lists open handoffs when a session starts, a status line that shows the context size — live in the vault's own configuration, outside this set ([ADR 0002](0002-external-tools-are-accelerators-not-prerequisites.md)).

## Consequences

- `adopt-pool` joins the teaching-and-assessment group; `assessment-layout` names `08-contributed.md` in the authoring stage, `adopt-pool` among the skills that fill it, and the handoff by its new name.
- `check.py` adds `critique-mcq` and `adopt-pool` to the checklists that carry the handoff clauses, `adopt-pool` to those that carry the approval exception, and requires the script clause of three skills by name.
- ADR 0020's exclusion of `critique-mcq` and its file name are superseded; the rest of it stands.
- A handoff a vault already holds under the old name is read by no resume clause; the run infers its step from the files and says so, and the vault can rename the file for its skill.
- A resumed critique still re-reads its report and measurement table — an estimate of 40K–60K tokens from the files' sizes, not a measurement — against a revision run at 450K.
- The scripts left in the second session's scratch folder are tied to that exam set's paths; making them general is work for the vault, not for this set.
